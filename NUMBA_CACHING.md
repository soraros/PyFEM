# Numba `cache=True` — stale-kernel hazard notes

Status: **preliminary** — root-cause investigation is in flight (PyFEM tower
mission M19). Sections marked ✓ are verified by two independent reproductions;
sections marked ⏳ await that investigation's report and will be updated.

These notes exist because the hazard was found here, but nothing in them is
PyFEM-specific: any package using `@njit(cache=True)` can be affected.

## 1. The incident (✓ verified)

While fixing a one-line bug in a `cache=True` numba kernel call path
(`pyfem/v3/fem/transforms.py`), we discovered that after editing the source:

- the **stale, pre-edit kernel was still served** from numba's on-disk cache
  (`__pycache__` next to the source file);
- this produced **false-green** results (old source + new cache → new tests
  "passed" against the stale kernel) and, in the opposite direction,
  **false-red** results (new source + old cache → correct code "failed");
- only clearing the package `__pycache__` produced truthful before/after
  measurements.

Reproduced independently by two different engineers (the fix author and the
reviewer), in both directions, on numba 0.62.1, CPython 3.13, macOS arm64→x86_64.

Naively this "should not happen": a source edit changes the function's
bytecode, and numba's cache key is supposed to change with it. The precise
mechanism that defeats invalidation for these kernels is the open question
(⏳ M19). Candidate mechanisms under investigation: factory-produced
dispatchers, decorator/qualname patterns, cache-key inputs that do not cover
the edited code path, dispatcher singleton reuse within a process.

## 2. Why it is dangerous

It silently corrupts exactly the measurements you trust most:

- **A/B and before/after benchmarks** (did my optimization do anything?)
- **regression/parity tests** (did the fix change the result?)
- **bisection** (the wrong commit can be convicted)

The failure is invisible: no warning, no error — just numbers computed by the
kernel you *didn't* ask for. In our case the before/after discrimination of a
~1e6-scale tangent error was at stake.

## 3. Policy we adopted (✓ in force here)

1. **No manual cache manipulation as a standing practice** — no blanket
   `__pycache__` clearing rituals, no per-checkout cache-dir surgery, unless a
   root cause proves it is the only option.
2. **Cache-unfriendly kernel code is a bug.** Every `cache=True` kernel is
   classified: (a) verifiably cache-friendly — invalidation provable under a
   source edit, keep; (b) cache-unfriendly — filed as a bug and fixed to be
   cache-friendly; or (c) caching explicitly disabled per kernel where (b) is
   impractical — a deliberate, documented choice.
3. **No unspecified behavior**: no code path whose behavior depends on
   unstated cache state.

## 4. How to check your own package (✓ methodology)

Minimal reproduction (run twice in the same checkout):

```python
# /tmp/cache_probe.py
import numpy as np
from numba import njit

@njit(cache=True)
def k(x):
    return x + 1        # <- edit this line between runs (e.g. + 2)

print(k(1.0))
```

```sh
python /tmp/cache_probe.py   # run 1
# edit k's body
python /tmp/cache_probe.py   # run 2 — same result as run 1 => STALE SERVE
```

Then the same probe against your real kernels: edit a line inside a
`cache=True` kernel (or a helper it inlines), rerun your test, and check
whether behavior tracks the edit without any cache clearing.

Warning signs you are exposed: kernels generated by factory functions,
decorators applied programmatically, dispatchers held as module-level
singletons, or `cache=True` on closures.

## 5. Measurement discipline until you know you're clean (✓)

For any before/after or A/B measurement of a `cache=True` kernel:

- clear the package `__pycache__` (or use a fresh `NUMBA_CACHE_DIR`) between
  the before and after runs, and say so in the measurement notes;
- treat any surprising before/after result as cache-suspect until re-run with
  a known-empty cache;
- in CI, either run benchmarks with a fresh cache directory per job or
  pre-warm and never edit sources between warm and measured phases.
